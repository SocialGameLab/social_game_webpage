# Match Room

A static site that shows how social-game-env
works. For each game it explains the rules and replays recorded matches played
by LLM agents. The lens switch lets you watch through one player's eyes: events
that player could not see are blacked out.

**Live site: https://socialgamelab.github.io/social_game_webpage/**

The site is plain HTML, CSS and JavaScript with no build step and no framework.
Only `site/` is published.

## Look at it

```bash
python3 -m http.server 8765 -d site
# open http://localhost:8765
```

Opening `site/index.html` straight from disk also works, because data files are
scripts, not fetches. Fonts come from Google Fonts; offline, the page falls back
to system fonts.

## Layout

```
content/                 hand-written copy (edit these)
  site.yaml              site title, home-page copy, optional source-repo link, game order
  games/<id>.yaml        one file per game: rules summary, "watch for" notes, runs to show
site/                    the published page (GitHub Pages serves this folder)
  index.html
  assets/css/            theme.css (tokens, dark mode) · base · layout · room · home
  assets/js/
    core.js              namespace, helpers, game registry, on-demand loader
    ui.js                shared building blocks: bubble, card, sys, block, banner, lens logic
    home.js              home page: intro, how-to steps, searchable game gallery
    app.js               routing, "How to play" and "Watch" views, playback, keyboard
  games/<id>/view.js     how one game draws its events, seats and board
  games/<id>/view.css    that game's board styles
  kinds/<kind>/view.js   a shared view for a family of games (rounds, deals, clues, table, race)
  data/                  GENERATED by tools/build_data.py, do not edit
    manifest.js          site settings, home copy, one card per game
    <id>.js              one game's copy and runs
templates/game/          starting files for a new game
tools/
  build_data.py          social-game-env demo/ bundles + content → site/data/
  new_game.py            scaffold a game from templates/game/
  check_site.py          consistency check (runs in CI before every deploy)
  build_single_file.py   inline everything into dist/match-room.html (for sharing as one file)
.github/workflows/pages.yml   deploys site/ on push to main
CLAUDE.md                conventions for extending the site
```

### How the page fits together

`index.html` loads `core.js`, `ui.js`, `home.js`, `data/manifest.js` and
`app.js`. The home page (empty hash) and the masthead's game menu are drawn
from the manifest alone. The menu is one `<select>` grouped by kind, so the
masthead stays the same size however many games there are. The gallery
adds search and kind filters once there are 7 or more games. When a visitor
opens a game, `MatchRoom.loadGame(id)` adds that game's
`games/<id>/view.css`, `games/<id>/view.js` and `data/<id>.js`. Only the
games someone looks at get downloaded; Jubensha's data alone is about 550 KB.

The core knows nothing about specific games. A game view registers hooks with
`MatchRoom.defineGame(id, {...})`. Every hook is optional, and the list is in
`site/assets/js/core.js`:

| Hook | Draws |
|---|---|
| `renderEvent(r, e)` | one log event in the feed (return `undefined` to use the shared renderer) |
| `chapter(e)` | entries in the "Jump to" menu |
| `board(r, evs)` | the right-hand panel, from the events the current lens has seen |
| `seatRole(r, p)`, `knowledge(r, p)` | the line under each seat, and its private info |
| `result(r)` | the end-of-game banner |
| `speaker(e)`, `rolesArePublic`, `onClick(t, r)` | who is highlighted, whether roles are secret, and extra controls such as the Jubensha verdict |

Use the `MatchRoom.ui` helpers (`bubble`, `card`, `sys`, `chapterHead`,
`block`, `banner`, `endBanner`, `openDialog`) and the color tokens in
`theme.css`, and a new game will look like the existing ones.

## Workflow

The recorded runs live in social-game-env, not here. That repo plays them and
exports each one as a bundle under its `demo/` folder, in a fixed format
(`run.json` plus the event log; see its `demo/README.md`). This repo only reads
those bundles, so it never imports the engine. The tools expect social-game-env
checked out next to this one (`../social_game_env`), or pass
`--demo /path/to/social_game_env/demo`.

```bash
# in social-game-env: record (calls the LLM), or just re-export after an engine change
uv run python -m runners demo record [game ...]
uv run python -m runners demo export

# here: rebuild site/data/ from demo/ and content/ (no model calls)
uv run --project ../social_game_env python tools/build_data.py
python3 tools/build_single_file.py         # optional: dist/match-room.html
```

`build_data.py` checks the bundles' `schema_version`, and stops if it is one it
does not know. The first prompt shown on each rules page, the players and the
result all come from `run.json`; this repo only slims the event log and merges
in the page copy.

### Change the copy

Edit `content/games/<id>.yaml`, or `content/site.yaml` for the home page, then
run `build_data.py`.

### Add a run to an existing game

Add the run to `demo/<id>/demo.yaml` in social-game-env and record it there.
Then add its `id` (with a `label` and `note`) under `runs:` in the game's
content file here, and rebuild. With more than one run, a picker appears above
the lens.

### Shared views

Most games don't need a view of their own. A game's content file can name a
kind with `view: rounds` (plus `view_options:`), and the page draws it with
`site/kinds/rounds/view.js`; or it can say `view_from: avalon` to reuse that
game's view. The kinds fall back on `MatchRoom.ui.autoEvent`, which renders
any event readably from its fields (seat numbers become names, `score0`/`score1`
become one per-seat value), so a game with an unusual event still shows text,
not JSON.

| Kind | For | Options |
|---|---|---|
| `rounds` | repeated matrix and economics games: a round-by-seat table | `round_events`, `round_label` |
| `deals` | negotiation: the latest offer, private values, settled rounds | `offer_events`, `round_events` |
| `clues` | secret-word and deduction games: the secret, this round's clues, results | `roles_public`, `redeal` |
| `table` | card and dice games: the latest move, each seat's status and private info | `move_events`, `out_events`, `round_event`, `round_resets` |
| `race` | dice and score games: a score bar per seat, the latest roll | `round_events`, `target_key` |

### Add a new game

```bash
python3 tools/new_game.py werewolf "Werewolf"   # creates content, view.js, view.css; adds it to site.yaml
# 1. fill in content/games/werewolf.yaml (rules, watch_for, runs)
# 2. in social-game-env: write demo/werewolf/demo.yaml, then record
uv run python -m runners demo record werewolf
# 3. here: build
uv run --project ../social_game_env python tools/build_data.py
# 4. open the page: events you have not drawn yet show as raw JSON, so you can see what the log holds
# 5. draw them in site/games/werewolf/view.js, and the board in view.css
```

If `runners.play` cannot drive the game, add an engine to `ENGINES` in
social-game-env's `src/runners/demo.py`. Game-specific data goes in the
run's `extras`, which `build_data.py` copies onto the run unchanged, so this
repo needs no change beyond the view.

## Deploy

1. Push this repo to GitHub.
2. Go to **Settings → Pages → Build and deployment**, set **Source** to **GitHub Actions**.
3. Every push to `main` runs `tools/check_site.py`, then publishes `site/`.
   Run the check locally before pushing.

To link the "Source of truth" paths on each rules page, set `source_repo` in
`content/site.yaml` and rebuild. Leave it empty while social-game-env is
private.

### Known caveats shown on the page

- **Bargaining is silent.** The action prompt's sample payload is
  `{"say": "", ...}` and the model copies the empty message. Fixing it means
  changing the prompt or the spec in social-game-env.
- **Jubensha "defend" assignments can be wrong.** The engine gives each
  question to the first character whose name appears in the answer key. In
  魔幻酒吧, 老J is told to defend the murder-weapon question because the key
  mentions his revolver, although the answer is 酒保小李.
- **Votes and mission cards are tallies.** The Avalon log records the
  approve/reject counts and the number of Fail cards, not who played what.
